# 后续增量更新工作规范

> 适用范围：Core、Android 独立进程、Gateway、PluginManager、跨端协议、流式取消、恢复链和相关文档的所有后续修改。
> 当前基线：`c3ba339`。当前验证：TS 581/581、JVM 132/132、`android-local-core-r8` 9/9、`AndroidModelTransportTest` 3/3。
> Android 支持声明：目前只有 FOA-AL00 / API 31 真机证据；其他版本和设备未验证，不作兼容承诺。

这是 Git 跟踪的规范文件。`custom/docs/` 中的计划、评审和证据是工作材料；若其当前摘要与本文或代码冲突，必须先修订工作材料，不得把历史快照当作当前状态。

## 1. 事实来源与当前状态

判断事实的优先级固定为：

1. 当前 `main` 代码和可复现测试结果；
2. 构建期生成物及校验结果（registry、protocol fixture、plugin manifest、bundle hash）；
3. 最新评审/证据文档；
4. 计划、旧评审和历史快照。

每次增量必须记录基线 commit、变更 commit、影响文件、影响契约、执行命令、实际结果、未覆盖风险和回退方式。测试未执行时必须写 `未执行` 或 `skip`，不得写成通过。

## 2. 变更分类

提交标题和证据必须使用以下分类之一：

| 分类 | 典型变化 | 额外要求 |
|---|---|---|
| `behavior-fix` | 取消、迟到事件、导演跨回合状态 | 先加失败行为测试，再修共享实现 |
| `contract-change` | API、owner、auth、响应形状、协议 envelope | 更新 registry/schema/fixture、所有 adapter 和跨端测试 |
| `android-boundary` | Binder、CoreService、Gateway、WebView bridge、恢复 | JVM 测试；有设备时做当前支持范围的 instrumentation |
| `generated-asset` | registry、manifest、embedded bundle | 重新生成并核对版本、字节数、hash；禁止手改生成 JSON |
| `test-only` | fixture、回归测试、证据脚本 | 说明测试触发的真实运行时语义，不得只作源码锚点 |
| `docs-only` | 状态、风险、规范更新 | 必须核对当前 commit 和测试数字 |

新增/删除/改名路由，改变 owner/auth/错误码/响应形状，或改变 requestId、turnId、revision、SSE、取消和插件 schema 语义，一律按 `contract-change` 处理。

## 3. 单个增量的执行顺序

1. 登记复现步骤、期望与实际行为、影响端和风险级别。
2. 定位共享 Core、registry、handler、adapter、Java 边界和既有 fixture。
3. 写出最小修改面及文件 owner；跨 owner 修改先停在契约评审。
4. 优先在共享 Core/handler 中修复；不得在 Android shim 复制桌面业务规则。
5. 先提交能稳定复现问题的失败测试，断言请求、事件、状态、取消或错误等可观察行为。
6. 实现修复，重建所有受影响的生成物。
7. 依次运行定向测试、全量 TypeScript、Android JVM；有可用设备时再运行 API 31 scoped instrumentation。
8. 生成增量证据，说明通过、失败和跳过；失败必须保留原始错误。
9. 合流前独立评审；P0/P1 未关闭不得放行。
10. 合流后重新运行受影响测试和全量回归，不能沿用分支上的旧数字。

## 4. 并发与合流

- 每个工作包必须声明 owner、分支、文件清单和依赖；同一文件同一时段只能有一个 owner。
- 推荐依赖顺序：共享契约/registry → Core/handler → Android adapter → 集成测试/证据。
- 未冻结契约只能由契约 owner 修改；其他工作包只能消费 fixture，不得猜测字段。
- 分支不得互相 cherry-pick 未评审的临时代码；由集成负责人合流并记录合流 commit。
- 阻塞一个工作包时，不得让其他工作包伪造其证据；无关工作仍可继续，但要写明依赖未满足。
- 冲突解决优先保留共享事实来源和测试，不得通过删除测试、放宽断言或静默降级来消除冲突。

## 5. 跨端和流式一致性

- 新行为先在共享 Core/handler 定义，再接入 Node、Android 本地和 Android 远程 adapter。
- 每个共享行为至少有成功、空态、错误、取消/迟到（适用时）fixture。
- Android 旧 shim 只能保留通用传输回退，不得新增业务路由或第二份业务规则。
- `transportId` 标识外部请求，`requestId` 标识模型请求；`turnId` 和 `revision` 决定状态作用域，四者不得混用。
- 流式修复必须同时检查逐块投递、客户端断开、上游取消、迟到结果、revision 和 active operation 清理。
- 导演模式必须单独验证；普通 chat 测试不能替代导演路径。

## 6. 测试与证据格式

每个增量证据至少包含：

```text
基线：<commit>
变更：<commit>
范围：<一句话>
定向测试：<命令> → <通过/失败/跳过数量>
全量测试：<命令> → <通过/失败/跳过数量>
Android JVM：<命令> → <结果或环境阻断>
设备：<型号/API/变体> → <结果或 skip>
生成物：<版本/字节数/hash，适用时>
未覆盖风险：<明确列出>
回退方式：<revert/旧路径/远程入口>
```

禁止以下替代：源码正则代替运行时测试、编译成功代替功能证据、历史数字代替当前结果、单台设备结果代替全 Android 支持声明。

## 7. 评审等级与介入点

- **P0**：数据损坏、凭据泄漏、跨进程边界失效、请求 A 写入请求 B 的状态。立即阻断合流。
- **P1**：取消不闭环、跨端响应不兼容、Core 崩溃拖垮主进程、owner 漂移、静默 404。修复并补行为测试后才能合流。
- **P2**：文档过期、极窄竞态、覆盖不足但不影响当前承诺。可以带风险合流，但必须登记责任和后续版本。

评审至少在四个节点介入：契约变更前；跨进程/取消/恢复/插件写入变更后；合流前；最终发布前。最终评审不得首次提出本规范已列出的基础边界问题。

## 8. Gate D 和 Android 支持范围

- Gate D 按 FOA-AL00 / API 31 的可验证范围收口。API 26–28、其他 API 29+、多设备矩阵和 release APK 不作为本项目硬验收条件。
- 设备可用时记录 Gateway UI、长 SSE、thinking、取消、Core kill/restart、renderer/Activity 恢复；无法执行的项目明确标记 `未验证`。
- 在最终开关决定前保留恢复页、远程入口和旧 shim。关闭 `legacyCoreBridgeEnabled` 或删除旧业务 shim 必须单独提交、可回退，并附新旧路径对照测试。
- 交付说明必须把“代码/测试通过”和“设备未验证”分开描述；不承诺所有 Android 版本兼容。

## 9. 文档与发布收口

- 当前状态只写在最新证据文档顶部和最新验收记录；R2-R11 等旧记录保留为历史快照并注明日期。
- 每次合流同步更新 `README.md`、`android/README.md`、pending 索引和受影响证据文档。
- 文档中的“待完成/暂缓/未通过”必须带日期和责任范围；状态改变后改成“历史状态”，不能留在当前摘要。
- 发布前必须完成：测试数字复核、生成物/hash 复核、APK 构建、秘密/私有数据扫描、回退路径检查和支持范围声明。

## 10. 增量完成定义

只有同时满足以下条件，增量才可标记完成：

- 问题可复现，或环境限制已明确；
- 修复位于正确共享层，或 adapter 特例有书面理由；
- 相关行为测试确实触发目标路径并通过；
- 生成物和版本/hash 一致（适用时）；
- 未覆盖风险、设备范围和回退路径已记录；
- 合流后定向测试和全量回归重新通过；
- Git 跟踪文档与当前代码、测试数字一致。

否则只能标记为 `待补证据`、`有条件通过` 或 `后续维护`。
