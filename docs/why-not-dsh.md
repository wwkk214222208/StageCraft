# 为什么不在 dsh 上直接改造，而是另起运行时

日期：2026-08-21

StageCraft 的核心运行时是独立实现的（自己的 HTTP、SQLite、状态模型、LLM 路由）。dsh 只是它的一个可选宿主——经 `dsh-rp` 以 Cordis bundle 嵌入，或者干脆跑成独立的 Node 进程。选择这条路线，不是图新鲜，也不是为了"重复造轮子"，而是因为把 RP 运行时建在 dsh 之上会踩到下面几个实际的问题。

## 1. dsh 的自指涉迭代能力，对 RP 没用

dsh 有个核心能力叫"自指涉"：AI 能在运行期间修改自己的代码、配置和工具。这套能力对"用 AI 写代码、维护系统"很有价值，但角色扮演（RP）不是这种场景：

- 剧本里的张三李四，不需要根据剧情去改写系统代码。角色靠的是内容状态的演进——记忆、性格、目标——而不是靠改动运行时。
- 一旦把"运行时"和"构建时"混在一起，让 AI 在剧情推进中直接改运行中的代码，维护会很快失控：同一份状态可能被代码改动、数据改动、配置改动同时影响，出事了既定位不了，也回滚不了，更没法审计。

RP 要的是"运行时稳定、内容可变"；dsh 提供的是"运行时自身也可变"。这两件事本身就是反着的，硬揉到一起只会两边都别扭。

## 2. dsh 的组件偏重，不适合直接拿来造 RP 的轮子

dsh 是面向"开发、运维 AI 工作台"设计的，它的组件是围着工程场景打磨的：严格的日志模式、审批流、会话生命周期、Agent 编排……这些对系统维护很有用，但不是 RP 需要的东西。

- 举个例子，dsh 的严格日志模式适合排查系统问题，但玩家维护剧情历史并不需要它。玩家关心的是"这条线当时是怎么走的、还能不能回到那个节点"，不是一份系统级审计日志。
- 把 RP 直接建在 dsh 的组件上，等于逼玩家去面对一套为工程师设计的界面和心智模型，这跟"傻瓜式、免折腾"的定位是冲突的。

## 3. dsh 的开放性来自 Cordis，不是来自 dsh 自己

dsh 能做到插件化、可扩展，根子上是底层 Cordis 容器的设计哲学在起作用。把 dsh 的组件和工具层剥掉，剩下的其实就是 Cordis 容器本身。所以：

- "在 dsh 上改造"和"直接用 Cordis 容器搭建"，能拿到的开放性其实是同一份来源；
- 但前者得背上 dsh 所有的组件负担，后者只要容器就够了，组件层可以自己按 RP 的需要来搭。

换句话说，既然要的是开放能力，直接用 Cordis 容器就行，不必再隔一层 dsh。本仓库锁定的就是 `@deepseek-ai/cordis` 4.0.0-rc.8；`docs/architecture.md` 也明确写了，Core Runtime 不依赖 HTTP、DOM、Cordis 或具体模型供应商。

## 4. dsh 适合用来维护 RP 系统，而不是取代它

分工应该是这样的：

- RP 系统本身（状态、角色、剧情、存储）由 StageCraft 的独立运行时承担，它得是稳定的、自包含的、能自托管的。
- dsh 的角色是宿主和维护入口：把 StageCraft 以 `dsh-rp` bundle 的形式嵌进 dsh，就能拿到沙箱隔离、调试桥、状态监控；真出了问题，也可以走 dsh 的调试入口介入检修。`dsh-rp/README.md` 里写得很直白——"DSH 保持 supervisor 身份"。

所以 dsh 是 StageCraft 的运行环境提供者和维护入口，而不是它的实现基础。前者是合理的集成方式，后者才是把方向搞反了。

## 现状对照

- `dsh-rp/`：StageCraft 的 Cordis/dsh bundle——同一份业务实现，打包成可安装的 dsh 插件；支持 `embedded`（进程内）和 `sandboxed`（子进程 + RPC）两种模式，dsh 只做 supervisor。
- `docs/architecture.md`：Core Runtime 明确不依赖 Cordis、HTTP 或 DOM——插件容器是宿主层的选择，不是核心的依赖。
- 运行形态：① 独立 Node 服务（`start.bat`）；② dsh 插件（`dsh-rp`）；③ Android APK（远程完整 UI / 本地嵌入 Core，实验性）。

## 小结

把 RP 直接建在 dsh 上，本质上是拿一个运维工具去当业务运行时用。StageCraft 自己实现的只是核心运行时那一层；至于宿主和维护能力，dsh 和 Cordis 仍然是可选的、可替换的。
