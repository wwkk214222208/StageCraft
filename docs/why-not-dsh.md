# 为什么另起轮子：StageCraft 独立运行时的架构理由

日期：2026-08-21

## 结论先行

StageCraft 的核心运行时是**独立实现**的（自己的 HTTP / SQLite / 状态模型 / LLM 路由），dsh 只是**可选宿主**之一（经 `dsh-rp` 以 Cordis bundle 嵌入，或独立 Node 进程运行）。这不是工程洁癖或重复造轮子，而是一组被反复权衡过的架构决策——把 RP 运行时建在 dsh 之上是**错误的方向**，理由如下。

## 1. dsh 的自指涉迭代能力对 RP 毫无用处

dsh 的核心能力之一是"自指涉"：AI 可以修改自身的代码、配置与工具，边跑边改。这对"用 AI 写代码 / 维护系统"的场景是核心价值，但对角色扮演（RP）是**无关甚至有害**的：

- 剧本里的张三李四，**不需要**根据剧情走向去迭代系统代码。角色应该靠**内容状态**（记忆、性格、目标）演进，而不是靠修改运行时。
- 一旦把"运行时"与"构建时"混在一起——即让 AI 在剧情推进中直接改运行代码——**维护难度会指数级上升**：同一份状态可能被代码修改、数据修改、配置修改同时影响，无法定位、无法回滚、无法审计。

RP 系统要的是**稳定的运行时 + 可变的内容**；dsh 给的是**可变的运行时**。方向不同，硬嫁只会两头不讨好。

## 2. dsh 的组件太重，不适合拿来造 RP 的轮子

dsh 是面向"开发 / 运维 AI 工作台"设计的，它的组件围绕**工程场景**打磨：严格的日志模式、审批流、会话生命周期、Agent 编排……这些都很好，但**不是 RP 需要的**：

- 例：dsh 严格的日志模式适合排查系统问题，但**不适合玩家维护剧情历史**——玩家要的是"这条线当时怎么回事、能不能回到那个节点"，而不是系统级审计日志。
- 把 RP 建在 dsh 组件上，意味着玩家被迫面对**为工程师设计的界面与心智模型**，与"傻瓜式、免折腾"的产品定位直接冲突。

## 3. dsh 的开放性来自 Cordis，不是 dsh 本身

dsh 的插件化开放性，本质上由底层 **Cordis 容器**的插件化设计哲学提供。剥掉 dsh 的组件与工具层，剩下的就是 Cordis 容器本身。因此：

- "在 dsh 上改造"与"直接用 Cordis 容器搭建"，两者得到的**开放性是同源的**；
- 但前者背着 dsh 的全部组件负担，后者可以**只取容器**、自由构建自己的组件层。

结论：要开放，直接用 Cordis 容器即可；不需要 dsh 这层中间人。事实锚点：本仓库锁定 `@deepseek-ai/cordis` 4.0.0-rc.8；`docs/architecture.md` 明确 Core Runtime"不依赖 HTTP、DOM、Cordis 或具体模型供应商"。

## 4. dsh 适合"维护"RP 系统，不适合"取代"RP 系统

正确的分工是：

- **RP 系统本身**（状态、角色、剧情、存储）：由 StageCraft 独立运行时承担——它必须是稳定的、自包含的、可自托管的。
- **dsh 的位置**：作为**维护者 / 宿主**存在——比如把 StageCraft 以 `dsh-rp` bundle 形式嵌入 dsh，获得沙箱隔离、调试桥、状态监控；出问题时可经 dsh 的调试入口介入检修。`dsh-rp/README.md` 说的正是这个：**"DSH 保持 supervisor 身份"**。

也就是说：dsh 是 StageCraft 的**运行环境提供者与维护入口**，而不是 StageCraft 的**实现基础**。前者是合理的集成，后者是架构错误。

## 现状对照

- `dsh-rp/`：StageCraft 的 Cordis/dsh bundle——同一份业务实现，打包为可安装的 dsh 插件；支持 `embedded`（进程内）与 `sandboxed`（子进程 + RPC）两种模式。dsh 只做 supervisor。
- `docs/architecture.md`：Core Runtime 明确不依赖 Cordis / HTTP / DOM——插件容器是宿主层的选择，不是核心的依赖。
- 运行形态：① 独立 Node 服务（`start.bat`）；② dsh 插件（`dsh-rp`）；③ 安卓（当前暂不推荐）。

## 一句话总结

**在 dsh 上直接改造 RP，是把"运维工具"误当成"业务运行时"。我们另起轮子的部分只有"轮子本身"（核心运行时）；需要宿主与维护能力时，dsh / Cordis 依然是可选的、可替换的车架。**
